# Renderer / backend integration contract

Targets public SDK >=0.18.0-beta.2, which is the installed app: `pi.ui.openLayer`, `@scope`-wrapped `injectStyle`, `workPanel.openView` and the `#pi-plugin-layers` stack all exist there, so this round ships as a plugin only. MAIN UI is React in public navigationSection and mainPage slots, both with props {}. Register mainPage with pageId rooms before navigationSection. Its host key is plugin:local.group-rooms/rooms. Create/Join save local requested form and synchronously pi.dispatch('shell.openPage', {pageId:'rooms'}) in the same click gesture; no awaited work may precede dispatch. Room rows call group-rooms.open and enter native chat. All main UI calls use pi.dispatch('plugin.call', {method,args}) → onRendererCall; every method and shell.openPage is declared in manifest. Disabling disposes both slots/styles/polling; host unregister returns an active plugin page to chat. Members WorkPanel and the unregistered fallback panel use window.pluginBridge.invoke → onPanelInvoke. No onPanelMessage API is assumed.

The UI calls these exact methods (all prefixed `group-rooms.`):

| Method | Arguments | Result |
| --- | --- | --- |
| `list` | `{}` | Portable `RoomNetworkStatus` + `listener?` + `listenerError?` + `listenerNotice?` + `picker` + `local: {label,address}` + `suggestAddress`. Never starts a listener, reconnects, or executes. Optional `label`. `local` is what this machine last called itself and the address it last handed out (written only by a successful `create`/`join`, so a failed attempt never remembers a typo); `suggestAddress` is the first non-loopback IPv4 this host's own interfaces answer, or `""` when there is none. Both are tiny, and the page prefers `local` over the probe so the Create/Join form is never retyped. |
| `snapshot` | `{roomId}` | Room fields + `runs` (newest 20) + `preferences: {targets: RoomSendTarget[], memberConfigs: RoomSendTarget[]}`. `targets` is always empty and kept only for shape compatibility. **No `messages` and no `workers`**: the UI draws none of it, and the room history alone pushed the answer past the host's 64 KB `plugin.call` relay limit after a few dozen messages — which failed this call on every 1.2s poll, blanked `room`, and left the `@` list empty. Both `snapshot` and `list` trim every room through one `roomView`: history and worker log dropped, `runs` cut to the newest 20 and any run still marked `running` reported as `unknown`. A poll answer is bounded by design, not by how long a room has been talking — the same room measured 196840 bytes before the projection and 8398 after. |
| `context` | `{context: {sessionId, managedByPlugin?} \| null}` renderer only | Save current native context; no execution. |
| `context` | `{}` panel/view | Return saved context or null. |
| `appearance` | `{}` renderer | Public `pi.app.getAppearance()` result (`locale`, `base`). |
| `selectDirectory` | `{}` | Starts the public native picker in the background and returns `{requestId,pending:true}` at once; the pick cannot answer its own call because the host times `plugin.call` out after 2s. The answer arrives as `list.picker = {requestId,pending,done,path,name,error}`; `pending` stays true until the dialog closes, `path` is null on cancel. One pick at a time. No room directory mutation. |
 | `create` | `{name,label,projectPath,address,port?}` | `{roomId,sessionId,invitation}`. Arms the listener itself (only a host ever binds) and uses its port when `address` omits one. Also approves **only the host's own member row**: this machine is the host, so asking its user to click 「批准助手」 on itself is the self-approval that was removed. Every other member, including one that joins and auto-requests, still lands as `pending` until the host approves. |
 | `join` | `{invitation,label,projectPath}` | `{roomId,sessionId,name}`. Dial-out only: joining never starts a listener. |
| `invite` | `{roomId,address,port?}` | `{invitation}`. Arms the listener itself, like `create`. |
| `open` | `{roomId}` | Open corresponding native session via confirmed public desktop operation. |
| `rename` | `{roomId,name}` | Void/JSON acknowledgement. |
| `requestAgent` | `{roomId}` | Void/JSON acknowledgement. |
| `approve` | `{roomId,memberId,approved:boolean}` | Void/JSON acknowledgement. |
| `revoke` | `{roomId,memberId}` | Void/JSON acknowledgement. |
| `leave` | `{roomId}` | Void/JSON acknowledgement. Leaving the last hosted room retires the listener (and stops the portable core); a guest leaving never had one. |
| `remove` | `{roomId}` | `{removed:true}`. Leaves the room **and** deletes this machine's own native room session, erasing its chat. The room is left first (leaving reads the room; the delete does not); a guest's `leave` would otherwise record the room so a rejoin keeps the old session, so that record is dropped before the delete and a later join creates a fresh session. `session/delete` is a dangerous host operation and still shows the native confirmation — that dialog is the user's own consent, not something the menu stands in for — so a refused or cancelled delete never fails the action and never rolls the leave back. The delete is **dispatched, not awaited**: the host holds its dialog open until the user answers, and a `plugin.call` is cut off after 2s, so awaiting it would answer this call with a timeout and then trip the relay breaker on the page's 1.2s polls (five consecutive timeouts = `PLUGIN_CALL_DISABLED`, 「插件刚刚连续出错」, 30s). The room is already left when this returns, so the dialog's answer changes nothing about the reply. |
| `configure` | `{roomId,memberId,modelKey,thinkingLevel?}` | Save per-member model config. Never executes or prompts, and never arms a send. |
| `cancel` | `{roomId,runId}` | Cancel an existing running turn, never submit a new one. |

`RoomSendTarget = {targetMemberId, modelKey, thinkingLevel?}`. `memberConfigs` covers approved members including local. There is no stored recipient list: an `@mention` decides who **else** runs, so `preferences.targets` is always empty. With no mention at all the sender is talking to their own computer, so the message is treated exactly like `@<this machine>` — the same approval, presence and saved-config rules apply, and a machine that is chat-only, unapproved or offline behaves as it does for an explicit self-mention. A message that names somebody else runs only them; this machine is never added as well. The members page edits models only. Both views and the composer read the same cached snapshot. Config UI never calls a provider catalog refresh. Configuration must remain available for offline previously approved members; @all chooses only online approved members with a model catalog, including local. Human/none/pending/rejected mentions send their member ID but broadcast without execution. Trigger marks use `label: '@<display name>'`, `send: '@<member id>'`; @all uses `label/send: '@all'`. Backend resolves mention IDs and revalidates online approval and catalog at actual send.

`list` reports `revoked: boolean` per room, projected from the core's persisted removal flag. A removed machine keeps the room and its history but is no longer a member: it cannot send (`ROOM_REVOKED`), the core never re-dials the host, and the UI must show 「已被移出房间」 rather than the plain 「已断开」 a transient outage shows. `roomState`/`roomStateText` in `shared.mjs` are the single source of that wording for all three surfaces (navigation rows, main page cards, members panel).

A member with no saved config anywhere runs on **its own machine's default model** (`isDefault`, else the first catalog entry). The core syncs each member's `selection` to every machine, and `member.selection` is what a peer displays for a member it does not configure locally; a local `memberConfigs` entry wins over the synced copy because that is what this machine sends with. `configure` writes the local preference and, for the member itself or the host, publishes `setSelection` to the room; that publish is display-only, so a failure is never surfaced. This replaces the earlier rule that a missing config must reject the send: a send must just work. An **explicitly saved** config stays strict — an unknown model key or an unsupported thinking level is still refused, and the fallback never silently stands in for a saved choice whose model left the catalog. `configure` still never executes or prompts.

The renderer performs a 1.2s **read-only** context/status refresh to detect approval/presence/session switches (public SDK has no session/context subscription). It guards generations, hides stale room controls, and syncs native context to the backend. The WorkPanel reads mirrored context on a 1.2s interval; responses are checked again against current context before display or mutation. Stale views disable actions immediately. The host singleton is `plugin:local.group-rooms/members`. The extension declares `plugin.call`, `session.readContext`, `shell.openPage` and `workPanel.openView`. It neither reads nor writes the composer draft any more. `workPanel.openView` is dispatched with `{viewId:'members', expectedSessionId}`, which the host accepts **only inside a trusted user gesture** and only while that session is the active one on the chat page; the extension therefore never calls it from a poll, and every entry point that reaches it does so from the user's own click or key press.

The backend must preserve host confirmation for `session/configure` and all worker operations, and therefore must never call `session/configure` on a routine path: the host re-confirms it natively on every call, so a per-send call becomes one dialog per message. This UI never configures `permissionMode` or sends `agent/prompt`, and the backend no longer narrows a worker's permission mode either — the worker runs at this machine's configured default. Native managed `onSessionSubmit` is the only chat entry.

The composer carries **no plugin controls**: who runs is decided solely by the `@mention` the user types, so the extension registers only the native `composerTrigger` '@' autocomplete (`mentionItems`). Models and thinking levels are set in the Members WorkPanel; `configure` publishes the choice as the member's synced `selection`. `shared.mjs` no longer exports a draft planner.

A reply states the model it ran on. The host renders a managed message's author as a byline and has no model column of its own, so the admitted run's `modelKey`/`thinkingLevel` become a `groupChat.modelLabel` (`<model label> · <level>`) on the finalized message and its streamed envelopes. The backend joins it with the member name (`byline`) and forwards that as the managed `author` for both `appendManaged` and `emitManagedEvent`, so a reply reads `🔵 Alice · Claude Sonnet · high`. The member name is prefixed with a colored dot chosen by a stable hash of the name, so the same member is the same color on every computer and across restarts; the host escapes markup, so an emoji is the only color a byline can carry. The palette is the seven chromatic circles — black and white are excluded, because a black disc on a dark transcript reads as a byline the plugin never colored. The run carries its own choice, so a reply keeps stating what it actually ran on after the member's selection changes. `memberName` stays the bare label because `workers.cjs` uses it as the quoted-history author; a member with no admitted model keeps the bare name.

The composer's own model chip follows **this machine's member choice**, not the app default. The host creates a managed session with no model bound, so the backend writes the member's saved `modelKey`/`thinkingLevel` onto the managed session via `session.setManagedModel` (a narrow, non-dangerous host call that writes only the model columns). It is written on `create`, on `join`, on `configure` of this machine's own member, on every persisted room snapshot whose own member selection changed, and once per saved room on activation. The choice has two records and both count: a local configuration wins, and the member row's synced `selection` is used when there is none — that is the only record a machine has when its member was configured from another computer. Only an **explicitly saved** choice is written; a member with none already runs on this machine's default, which is what the chip would show, so writing it would be a call that changes nothing. An unchanged binding is never written twice. The chip is host-rendered and read-only; this UI never writes it.

A room message carries attachments as **content-addressed descriptors only** (`RoomAttachment = {ref, name, kind, mimeType?, size?, inlinePath?}` with `ref = attachments/<sha256>`), never bytes: a room message is capped at 100000 bytes and the history at 512 KiB. The host content-addresses a composer attachment before it reaches the plugin, so `onSessionSubmit` receives descriptors whose bytes already sit in this machine's store. A message with an attachment and no text is valid. The bytes move out of band in 256 KiB chunks through the host, the only machine everyone is connected to; each member pulls a blob it lacks, stores it content-addressed, and re-announces the message so the transcript re-renders. The `@mentioned` worker receives the attachment as a content-addressed prompt path. A failed transfer never blocks the message. One attachment is capped at 50 MB and one message at 32 attachments; over either, the send is reported, not silently dropped.

The composer names an attachment in the message body with the same `@"<path>"` text an ordinary session uses, and the host reports that text as the descriptor's `inlinePath`. It is kept for two reasons: it is what places the picture between the words it sat between in the native transcript, and it is what `submit` removes before reading mentions. A path is not a room member, so leaving it in made a photo sent with `@all` die with `Mention must identify exactly one room member`. Exactly the text the host attributed to an attachment is stripped — a quoted `@path` the user typed by hand still reads as a mention and is still refused.

The management page seeds its Member name and Address fields from `list.local` (falling back to `suggestAddress`, then a placeholder) once, on the first answer, and never overwrites something the user is already typing; a machine whose name is already recorded in a room's member rows uses that first. Every address field — Create, Join, the room card's invitation form and the row menu's inline form — stays editable, because a multi-homed box may probe the wrong NIC. A successful `create`/`join` opens the new room's native session in the same submission through `open`; `session/open` needs no click gesture of its own, so this is a plain `call`, not an `action`, and never nests the busy flag. Room rows carry a hover-revealed `…` button whose menu is portalled into a **`pi.ui.openLayer()` layer**, never `document.body`: the sidebar clips its rows so the menu cannot live in the row, and a body portal would arrive with **no plugin CSS at all**, because `pi.ui.injectStyle` wraps every rule in `@scope ([data-pi-plugin="<pluginId>"])` (one exception) and the layer element is what carries that attribute. Its items are Open session, Room members, Rename… (host only), Create invitation… (host only), Leave room, and Delete room. Rename and invitation open a small inline form in that same layer instead of sending the user to the management page. Delete is a two-step inline confirm, and then the native `session/delete` dialog is a second, unavoidable one (see `remove` — the reply does not wait for it). **Generating an invitation copies it in the same step**: a row-menu invitation would otherwise leave the newest invitation in a store field that the management page — not mounted while the user is in the sidebar — is the only surface that renders, so the user asked for a copy they could not see and got nothing on the clipboard. The copy goes through `navigator.clipboard.writeText` with a detached-field `execCommand('copy')` fallback, and the field is created by the plugin rather than borrowed from the page, so it works with no management page mounted. A refusal is reported as a refusal (「请点「复制」，或手动选中内容复制」), never as a success notice; the page's own 「复制」 button remains for that case. The menu is positioned `fixed` against the row's viewport rect; the layer is zero-sized and unpositioned, so the rect still resolves against the viewport. The sidebar sets no `transform` today, so a host that adds one would offset the menu.

Entering a room opens the members panel **on the first user gesture after the switch** (`pointerdown`/`keydown`, capture), because create/join completion is asynchronous and carries no gesture for `workPanel.openView` to run under; the one-shot is consumed either way and expires after 15s. It is armed on the **active session id**, not on the room: resolving which room a session belongs to takes a 1.2s poll, and a user arriving in a room presses something well inside that window. One gesture dispatches **once** — a single handler registered for both event kinds would fire twice per click, and the host keeps one singleton tab per plugin view, so the second dispatch re-opens the tab with no view behind it. A `成员` chip on the selected row, a `Room members` row-menu item and a `房间成员` button on the room card are the explicit entries for when the automatic one has already fired; they are also the only way to open it again, since closing it is respected. The chip and the row's `…` button share the row's right corner, so the chip reveals on the same hover as the button and reserves the button's column with its own right margin — both visible together, neither painted over the other, and neither covering the title.

A host room with a `pending` member raises a `.p-overlay`/`.p-dialog` approval prompt (稍后 / 拒绝 / 批准) built from the host's own dialog classes inside a plugin layer; 稍后 is remembered per `roomId:memberId` for this page's lifetime so it does not nag, and the row keeps a `待批准` chip so a dismissed request is never lost. 批准/拒绝 go through `approve`; approving or declining then opens the members panel. The host's `.p-dialog` shell is a **translucent** surface (`--ds-bg-elevated`, 4% clear in dark and 30% in light) and its tool classes style no buttons, so the plugin's own `.gr-approval.p-dialog` rule restates the opaque `--ds-bg-elevated-opaque` surface and styles `.p-dialog__foot button` itself. Both selectors name `.p-dialog` because the host's rule has the same specificity and the stylesheet order is not this plugin's to decide; the host's `.p-dialog__foot` already flex-aligns its children, so the plugin only adds the wrap.

A run whose target never received a terminal receipt stays `unknown` in the room, and the core's `admit` refuses every later message to that member ("Agent already has an active or uncertain run") until something releases the record. That guard is what keeps a possibly-live turn from being double-started, so it must never be released on suspicion — but a run **this machine's own worker has settled** can never be released by anyone else: the core only clears an `unknown` run through a successful host re-admission, and a turn the local worker gave up on has no host left to re-admit it. The plugin therefore calls a build-time-injected `forgetRunStatus(roomId, memberId, statuses)` in exactly two places: once per saved room on activation, and once before a send is journalled. The proof is the local worker journal, not the room label: a run the worker is still tracking (`pending`/`running`) is left alone however the room happens to mark it, and only a run this machine owns with a stated model is eligible. The injection lives in `lib/core-patches.cjs` so the portable candidate tree stays pristine; it is the plugin's second and last addition to the core, after `forgetDeparted`.

A machine only leaves cleanly while its link is up. A guest whose app was relaunched with its stored room lost (reinstall, cleared data, a crash before the leave landed) rejoins with a fresh credential while its old row is still on the host, offline — and the core's `join` cannot match it, because it authenticates by credential and a join mints a new one. The join used to add a second row for the same name that nothing ever retired, so the members list grew one ghost per rejoin, on **both** machines (a guest's view *is* the host's snapshot). The plugin's third core injection therefore retires, inside `join`, every offline row carrying the joining name — a name is one computer's identity here — together with its credential, and marks its still-`running` runs `unknown` exactly as `revoke` leaves them. A clean rejoin never reaches this: a connected member is matched by credential and resumes. Existing rooms converge on their next rejoin; a room that already holds a ghost does not self-heal until then. The injection lives in `lib/core-patches.cjs` alongside `forgetDeparted` and `forgetRunStatus`.

Backend integration: context, appearance, configure and snapshot.preferences.memberConfigs must be available; source namespace and manifest sessionSources both use group-rooms. `list` remains inert. There is no listener switch: hosting is receiving, so `create`/`invite` arm the listener, a saved host room re-arms it on activation (remembering the port and bind address, reported as `listenerError` if it cannot), and leaving the last hosted room retires it. If the remembered port is taken, the action still succeeds on an automatic port but `listenerNotice = {from,to}` tells the page that already-shared invitations are stale; a fresh `invite` clears it. A machine with no host room stays network inert on activation. The UI intentionally does not change joined paths: portable service has no directory setter; leave/rejoin selects another local directory. The unhandled legacy group-rooms-plugin.open command and its activation event were removed along with ui.panel; MAIN navigation is the management entry. Host/backend integration is owned by the parent agent.

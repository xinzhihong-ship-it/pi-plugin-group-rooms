# 群组房间（Group Rooms）

在 PI-Desktop 主侧边栏的「会话」「项目」之后新增一个**群聊**分类：创建或加入共享房间，
在**原生会话**里聊天，在**工作面板**里管理成员。

- 插件 id：`io.github.xinzhihong.group-rooms`
- 版本：`0.1.0`
- 源码仓库：<https://github.com/xinzhihong-ship-it/pi-plugin-group-rooms>

> **一句话理解**：房间本身不跑 AI。你 `@` 谁，谁就在**自己那台电脑上**用自己的模型执行，
> 结果回到同一个原生会话里。聊天记录是宿主原生会话，不是插件自造的界面。

---

## 一、依赖与运行环境

### 1. 宿主版本（硬性要求）

```json
"engines": { "piDesktop": ">=0.18.0-beta.2" }
```

插件用到的宿主公开 API —— 托管原生会话与转写、插件私有密钥、agent 事件订阅、
原生工作面板动作、主壳导航/页面插槽 —— 从 **PI-Desktop 0.18.0-beta.2** 起提供。

- **0.18.0-beta.2 及以上**：满足版本门槛，`pi.ui.openLayer()`、`@scope` 包裹的样式注入、
  `workPanel.openView`、`#pi-plugin-layers` 层栈都已存在。
- **0.17.x（正式版）**：**不支持**。它没有上述托管会话与密钥 API，且它的 PluginCheck
  会直接拒绝本插件声明的 `session.manage.own` 与 `secrets.store` 两项权限。

### 2. 宿主补丁（前置条件，重要）

本插件依赖一组**尚未合并进上游 `main`** 的宿主能力，已作为上游 Issue / PR 提交：

- Issue：<https://github.com/vastsa/PI-Desktop/issues/1539>
- PR：<https://github.com/vastsa/PI-Desktop/pull/1540>

**在 PR #1540 落地、或宿主已打入等价补丁之前，本插件无法在正式版上运行。**
缺失的能力包括：托管原生转写与提交回执、非危险的托管会话模型绑定
（`session.setManagedModel`）、托管会话附件搬运、加密的插件私有密钥、按会话的
agent 事件流与终态回执、生命周期持有的 `navigationSection` / `mainPage` 插槽。

### 3. 插件自身的依赖：**零 npm 依赖**

打包产物 `.piplug` 内**不含 `node_modules`**，安装时不需要联网拉包：

- WebSocket 服务端/客户端库（`ws`）已**内联**进 `lib/network.cjs`（约 19 万字节）。
  其许可见 `lib/WS-LICENSE.txt`。
- `bufferutil`、`utf-8-validate` 是 `ws` 的**可选原生加速件**，在 `lib/network.cjs` 中
  位于 `try/catch` 内并受 `WS_NO_BUFFER_UTIL` 门控：**缺失时自动降级为纯 JS 实现**，
  不影响功能，只是吞吐略低。无需安装。
- 其余全部是 Node 内置模块：`node:os`、`node:crypto`、`node:https`、`node:tls`、
  `node:util`、`net`、`http`、`https`、`tls`、`stream`、`zlib`、`buffer`、`events`、`url`、`util`。

> 结论：**只需一个满足版本要求的 PI-Desktop，无需任何额外安装步骤。**

### 4. 重建网络核心（仅开发者需要）

`lib/network.cjs` 是从保留的候选核心打包出来的。重新生成：

```bash
node build.mjs <candidate-worktree>
```

构建期补丁在 `lib/core-patches.cjs`，使用严格源码锚点。运行时不需要候选仓库路径。

## 二、安装

1. 确认 PI-Desktop 版本满足 `>=0.18.0-beta.2`，且已包含上面「宿主补丁」所述能力。
2. 从插件中心安装，或在本机安装 `.piplug` 包。
3. 在「扩展」里打开**群组房间**开关。关闭开关会注销导航分类、管理页与原生 `@` 补全，
   把正在打开的管理页切回聊天，但**保留房间数据与原生聊天记录**；重新打开即恢复房间列表。

## 三、使用说明

### 创建房间

1. 左栏「群聊」分类里点**创建**。
2. 填**成员名称**（这台电脑在房间里的名字）与**其他电脑可连接的地址**。
   两者都会**记住**，下次自动预填（见下文「本机记住名字与地址」）。
3. 选择**本机可访问的项目目录**。若项目在 NAS 上，**先把 NAS 挂载好**再选它的本地挂载路径。
4. 提交后**直接进入该房间的原生会话**，并自动打开**成员面板**。

### 加入房间

1. 左栏「群聊」分类里点**加入**。
2. 粘贴**邀请码**，填成员名称，选择本机项目目录。
3. 提交后同样**直接进房**。

加入时会在**同一步**顺带申请 agent 权限：只加入不申请，是「`@` 了却没人回」最常见的原因；
而本机用户既然主动加入，即视为已同意。该申请在宿主批准前保持 `pending`。

### 聊天与 `@`

房间的原生会话就是聊天窗口，**用宿主自带的输入框发消息**，没有插件自造的输入框。

- 消息里**不带任何 `@`**：在**本机**执行，等同于 `@` 自己。
- `@某人`：**只有那个人**执行。
- `@all`：房间内所有人各自执行。

执行者由你输入的 `@` 决定；**选择模型或选择成员都不会触发执行**，原生提交才是执行入口。

### 成员面板

点选中的房间行上的「成员」胶囊、房间行 `…` 菜单里的**房间成员**、或管理页房间卡片上的
「房间成员」，都会打开既有的**工作面板**。里面可以做：批准/拒绝成员、按成员配置模型与思考等级、
选择收件人。

### 房间行菜单

左栏「群聊」列表里，每个房间行悬停时右侧出现一个 `…` 按钮（和原生会话行一致）。菜单项：

| 菜单项 | 说明 |
|---|---|
| 打开会话 | 进入该房间的原生会话 |
| 房间成员 | 打开成员工作面板 |
| 重命名 | 仅房主；行内小表单 |
| 生成邀请码 | 仅房主；生成后**立即复制到剪贴板**并提示 |
| 离开房间 | 离开，保留本机聊天记录，之后可用邀请码重新加入 |
| 删除房间 | **离开 + 删除本机那个原生会话**（聊天记录彻底消失） |

**关于「删除」**：会弹**两次**确认 —— 菜单里一次，宿主的危险操作确认框一次，这是有意的。
删除**不等待**宿主确认框：你在菜单里一确认，房间立刻离开，删会话在后台结算，
所以把确认框晾着也不会卡住插件。若取消宿主的确认框，房间**已经离开**，会话会残留，
可在原生侧边栏手动删除。被删除的房间**不会**被后续重新加入接回旧会话。

### 本机记住名字与地址

- **成员名称**：优先取房间已有的成员行（最权威的记录），否则取上次用过的名字。
- **可连接地址**：优先用本机上次对外给出的地址；没有时，插件**探测本机网卡**，
  给出**第一个非回环 IPv4**。
- 所有地址输入框**始终可改**：多网卡机器（Wi-Fi + 有线、NAS 或 VPN 网卡）可能探错，
  **你填什么就记什么**。
- 只有**真正创建或加入成功**的房间才会被记住，所以打错的地址不会被下次表单沿用。

### 待批准提示

当别的电脑的助手在等这台宿主批准时，房间行会显示 `待批准` 胶囊，**并弹出一个对话框**，
提供**稍后 / 拒绝 / 批准**。批准和拒绝立即生效；「稍后」关掉该对话框，本次会话内不再弹出，
但胶囊仍可找到该请求。

## 四、设置项（插件私有，存于宿主设置文档 `groupRoomsBackend`）

插件**没有**自建设置界面；所有状态存在宿主的插件私有存储里（`pi.plugin.getSettings()` /
`setSettings()` 的 `groupRoomsBackend` 文档）。主要字段：

| 字段 | 含义 |
|---|---|
| `local.label` | 本机在房间里的成员名称（跨房间记住） |
| `local.address` | 本机上次对外给出的可连接地址（跨房间记住） |
| `preferences` | 按房间、按成员保存的模型与思考等级 |
| `listenerPort` / `listenerBind` | 宿主房间的监听端口与绑定地址（记住以让已发出的邀请继续有效） |
| `workers` / `workerSessions` | 本机 worker 会话记录 |
| `secretKeys` | 已保存的插件私有密钥的引用名 |
| `submissions` | 提交/回执记录 |

> **注意**：房间的**聊天记录本身不在**这个文档里 —— 它是宿主的原生托管会话
> （`managedByPlugin` = 本插件 id），因此改插件 id、重装、清理插件设置都**不会**丢失聊天历史。

## 五、权限说明

| 权限 | 为什么需要 |
|---|---|
| `desktop.control` | 通过宿主桌面操作创建/打开/删除会话，驱动本机 worker |
| `session.manage.own` | 托管本插件自己的原生会话（房间转写、worker 会话） |
| `session.read.own` | 读取本插件自己会话的上下文（项目路径等） |
| `secrets.store` | 用宿主加密存储保存房间密钥等敏感值 |
| `ui.view` | 注册「房间成员」工作面板视图 |
| `renderer.extension` | 注入原生 `@` 补全、导航分类与主内容页 |
| `background.service` | 插件后台服务：接收/维持房间网络连接 |
| `fs.read` | 读取用户选定的项目目录（`root: userSelected`，范围由用户选择决定） |
| `models.list` | 读取模型目录，供按成员选择模型 |
| `net.anyHost` | 房间是点对点/局域网通信，需连接任意主机 |

## 六、外部服务与网络

- **没有第三方云服务**。房间是**局域网内点对点**通信：房主监听，成员主动拨入。
- 托管与转发走**宿主**（大家共同连接的那台机器），用于搬运附件等二进制数据。
- 附件按 256 KiB 分块传输；单条消息最多 32 个附件，单个附件上限 50 MB。
- **承载即接收**：创建房间或生成邀请会启动监听；已保存的宿主房间在激活时会按记住的端口
  重新监听；离开**最后一个**宿主房间则停止接收。没有任何「监听开关」——
  **创建房间本身就是同意接收**。不承载任何房间的机器在激活时保持网络静默。

## 七、已知行为

- **未配置模型的助手**用**它自己电脑的默认模型**执行。所以 `@all` 只是发送：
  不需要先给谁配模型，也不会因为「没选模型」而拒发。每个成员的模型与思考等级会同步到房间，
  成员页能看到每台电脑在跑什么，包括本机从未配置过的那台。
- **显式保存过的配置仍然严格**：未知模型键、不支持的思考等级、已下架的模型，一律拒绝，
  不会静默替换成默认值 —— 回退绝不顶替你刻意做的选择。
- **agent 回复会标明它实际运行的模型与思考等级**，作者名带颜色点。
  例如 `🔵 Alice · Claude Sonnet · high`。颜色由名字的稳定哈希决定，
  同一成员在任何电脑、重启后都是同色；调色板是七种彩色圆点（黑白刻意排除，
  因为深色转写上的黑色圆点看起来像「没上色」）。
- **被移出的成员在自己屏幕上可见**：保留房间与历史，但不再是成员，
  导航行、管理页卡片与成员面板都显示「已被移出房间」，发送也会被同样措辞拒绝。
- **worker 会话不会自动删除**，它们留在本机侧边栏作为执行记录。断开或中断的运行记为
  `unknown`，**绝不重放**。
- **worker 使用本机自己配置的默认权限模式**：插件**从不**调用 `session/configure`
  —— 那是危险操作，每次调用宿主都会重新弹原生确认，逐次调用会让每条房间消息都弹一次框。
- **房间转写不绑定任何宿主项目**，也不会创建项目。它是托管会话，永远不跑 agent。
  （早期版本为它建项目，导致一打开房间侧边栏就冒出用户没要的项目，而插件无法撤销提升。）
- **长会话不会撑爆 `@` 列表**：房间回答经宿主 `plugin.call` 中继，超过 64 KB 会被拒。
  `snapshot` / `list` 现在只回一个裁剪过的投影（丢弃历史与 worker 日志，运行日志只留最新 20 条），
  所以轮询应答不再随房间对话变长而增长。

## 八、兼容性

- **要求**：PI-Desktop `>=0.18.0-beta.2`，**且**宿主包含 PR #1540 / Issue #1539 所述能力。
- **不支持**：0.17.x 正式版（缺 API，且其 PluginCheck 拒绝 `session.manage.own`、`secrets.store`）。
- **尚未完成实测**：物理多机、跨操作系统（Mac ↔ Windows）、真实远端权限卡片的接受流程。
  已在单机双实例（宿主 + 客机）用本地 SSE fixture 完成网络执行验证。
- 详见 [`COMPATIBILITY.md`](./COMPATIBILITY.md)。
